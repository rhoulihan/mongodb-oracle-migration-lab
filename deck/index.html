Three doors and one room

Pick by what you can afford to lose, and how long you can be down.

Optimization is not a fourth door. It is the room behind all three.

Start with the axes. Left to right is downtime: near zero on the left, a planned window on the right. Bottom to top is reversibility: a one-way door at the bottom, a door you can walk back through at the top.

Click. Door A, age out. From day N every new write goes to Oracle, and only the long-lived data moves. Near-zero downtime. Slow, because the old system hangs around as a read-only archive until the retention clock runs out. It's a door you close slowly.

Click. Door B, dump and restore. Stop writes, mongodump, mongorestore, validate, flip the connection string. Planned downtime, and fast. Once writes land on Oracle, the door locks behind you. You can delay the lock, and segment 3 shows how. You can't remove it.

Click. Door C, blue/green. Both systems live, a replicator keeping Oracle in step, a flip with no downtime, and a reverse path so you can walk back. The most reversible door. Also the most moving parts.

Click. Now the room. Optimization is not a fourth strategy. It's what you do once you're through the door, and each door gives you a different amount of time and freedom to furnish it. Age out hands you a greenfield. Dump and restore is lift first, remodel in place later. Blue/green lets you remodel during the move, as long as the old document shape is still a projection you can produce for the fallback.

Land: the question isn't how to move the data. It's what you can afford to lose, and for how long you can be down.

The API gets you in. The engine behind it is why you stay.

Before we pick a door, the reassurance. For most of you, this is lift and shift.

The app keeps its code and its MongoDB driver. The Oracle API for MongoDB speaks the MongoDB wire protocol, so the change is the connection string. The data moves with mongodump and mongorestore, the tools your team already runs.

I did this to myself. Post 46. My personal app server ran on Atlas free for years, and about 90% of what it stores is transient: rate limiters, ephemeral state. I moved it to Autonomous Database Free. Easiest migration I've ever done. One gap: no $near. I closed it with $sql, Oracle's pipeline stage that runs a SQL statement inside db.aggregate(). The hardest part was finding the connection string in the OCI console.

Now be precise about what compatibility buys you. Wire-compatible is not identical. The gaps are edge-shaped: a type that reads back fine and queries differently, an operator that isn't there on your build. Segment 1 finds them before they find you.

Land: plan for boring. A boring migration is a successful one.

Segment 1 · Discovery 0:05 · 10 min

Inventory the workload, not just the data

Ask how long each piece of data stays useful. Some of it never needs to move.

Start with what discovery usually gets wrong. Teams inventory the data: collections, sizes, the index list. Necessary. It's not what picks the door.

What picks the door is how long each piece of data stays useful. The axis is log scale, a minute to ten years. Subscribers, accounts, the catalog, regions: entity data. It lives as long as the customer, and new records point at it. It moves whatever door you pick.

Orders are event data. They age out under a retention policy. With age out they stay behind as a read-only archive. With the other two doors they move.

Now the clocks. orderEvents carry a TTL index, time to live, on createdAt: seven days and the database deletes them. Carts: 120 seconds. In this lab the carts are spread over about four hours after load, so they're expiring while we talk, about 21 a minute. Sessions, rate limiters, caches, carts: transient data never needs migrating. It needs to expire on the side it was born on.

One trap, planted on purpose. orderEvents also carry a field called ts, and it's a BSON Timestamp, not a Date. A TTL index only expires Date values. Put the TTL on the Timestamp and it deletes nothing, with no error. Ours sits on createdAt for exactly that reason.

The rest of the inventory: growth and write rates, every index, feature use (change streams, Atlas Search and $vectorSearch, Atlas triggers, $graphLookup, geo operators, transactions, server-side JavaScript), and your driver and Database Tools versions. Each one changes the plan.

Land: the cheapest bytes to migrate are the ones you let expire.

Segment 1 · Discovery 0:08

Find the landmines before they find you

Five BSON types that survive the move and still change what a query sees.

This is the slide that bites in production. Slow down.

Some BSON types have no Oracle JSON scalar. A regex and a BSON Timestamp land as tagged objects, $regularExpression and $timestamp. Read the document back and it looks right. Now ask for {$type: 'regex'} and the Oracle API rejects the filter: '$type value not supported'. Same for timestamp. A query that found every regex field on MongoDB is an error on Oracle.

Int64. We planted one order whose version is 2^53 plus 1. mongorestore carries it across exactly. Then $inc it by 1 through the Oracle API and it stores 2^53. Exactness gone, no error.

Decimal128. The value survives. The scale doesn't: 19.00 reads back as 19, and 1.10 as 1.1. Equal as numbers, different as text. If a report prints the stored value, format it in the app.

Arrays. On MongoDB, {lines: {$type: 'object'}} matches an order whose lines array holds objects: MongoDB looks inside the array. On Oracle it doesn't. Same data: 2,000 matches on MongoDB, zero on Oracle.

None of this blocks a migration. All of it fails quietly if nobody looks. Demo 1 runs a type census on the source, so you know which fields carry these types before you move a byte. Demo 3 runs the differential after the restore.

Land: reads the same, queries differently. Find them first.

Segment 1 · Discovery 0:13

Which door? Start with these factors

We come back to this at the end, with every door filled in.

Now the factors that pick the door. Read each row as: if this is true, it pushes you toward that door.

Short data life cycle, days to months: age out. Let it expire where it lives.

A downtime window, and a data volume that fits it: dump and restore. Size the window from a rehearsal, not an estimate.

No downtime allowed, or rollback is a hard requirement: blue/green.

Legal retention on the old data: age out keeps the old system as the archive. Or you move all of it with B or C.

Heavy join and aggregation pain today: any door, plus the optimization track. That's the green row, and it's segment 5.

Running two systems: age out and blue/green both need a team that can operate two databases for a while. Dump and restore doesn't.

Budget for replication tooling and a parallel stack: blue/green.

And hybrids are normal. Age out the event data, dump and restore the entity data. Or dump and restore now, with blue/green-style sync for the one collection you can't freeze.

Land: no door is best. One door is best for your workload.
Segment 2 · Strategy A 0:15 · 12 min

Age out: move only what lasts

Day N: new writes go to Oracle. Old orders stay put, read only.

Strategy A, age out. Five steps, and this picture is the first four.

Stand up Oracle. From day N, every new write goes to Oracle. Then move only the long-lived entity data that new records point at. In our lab that's regions, the catalog, accounts and subscribers. Orders stay in MongoDB.

The box on the left is step three: a data access layer in the app tier that routes each read by the cutoff. placedAt on or after the cutoff reads Oracle. Older reads MongoDB. A read that spans both fans out and merges.

Step four: MongoDB goes read-only. It's an operational archive now. In the lab, a PATCH on an old order returns 400. Read-only has to mean read-only, or the seam leaks.

Watch the bottom box. Carts and order events keep expiring in MongoDB on their own TTL clocks. Nobody moved them. Nobody needs to.
Segment 2 · Strategy A 0:15 · 12 min

Age out: move only what lasts

As old orders age out, the archive shrinks.

Step five, and it's the slow one. Time passes. Old orders age past retention and leave the archive. The MongoDB box shrinks. Oracle grows with every new order.

How long this takes is set by your retention policy, not your project plan. Months for short-lived event data. Seven years for regulated records, and seven years of retention is seven years of a second database. Hold that thought for two slides.

Retention passes. Nothing left in MongoDB is needed by the business. Switch it off. One database again, and the router comes out of the app.

Segment 2 · Strategy A 0:18

Where age out leaks

Every seam is new app code.

Cross-cutoff reads

Fan out to both, merge in the app.

New order, old customer

Move the customer first.

IDs

Keep ObjectId on both sides.

Read-only means read-only

Any write to the old side drifts.

Now the seams. Every seam is new app code, and new code has new bugs.

The cutoff. Where is the line, and is it clean? In the lab it's deterministic: the newest legacy order plus one millisecond. Any query that spans the line fans out to both systems and merges in the app tier. Reports that cross the cutoff are the usual victims: sorting, paging, totals. Demo 2 proves our merged read is correct. Your reports have to prove it too.

Referential seams. A new order references an old customer. That only works if the customer moved first, and that's why the entity versus event split decides the move order.

IDs. Keep ObjectId on both sides, so an _id means the same thing whichever system holds the document. Our router looks up an old order by _id, misses on Oracle, and finds it in the archive.

Read-only means read-only. If anything still writes to the old side, the archive drifts and the merged read serves stale facts. In the lab, a PATCH on an old order returns 400.

And the derived data. Our dashboard's Top-N on Oracle covers only orders after the cutoff, so a region with no new orders yet shows 'no Top-N'. Decide up front whether derived views rebuild from new data only, or get seeded.

Land: age out is cheap on data movement and expensive on seams. Count the seams before you pick it.
Segment 2 · Strategy A 0:20

The cost: a second database for years

The polyglot tax, applied to ourselves.

2 patch cycles2 login models 2 attack surfaces2 backup plans

Way out: when the rest goes cold, move it in one small dump and restore.

The risks. The big one is the one I spend my career warning about in other people's architectures.

Two databases for the life of the window. Two patch cycles, two auth models, two attack surfaces, two sets of backups, two on-call runbooks. That's the polyglot persistence tax, applied to ourselves. Say it plainly to the customer.

Second: 'temporary' archives become permanent. Nobody schedules the decommission, and the retention window keeps getting extended.

Third: the long tail. Seven-year retention means seven years of MongoDB. The way out: once the residue is cold and read-only, move it in one final bulk dump and restore. A small Strategy B at the end, with a window nobody notices, because nothing writes there anyway.

And decide what 'deprecate' means before you start. Frozen and read-only in place, or exported to object storage and queried in place. Pick one in the plan, not in year three.

Land: age out is the gentlest door to walk through and the easiest one to never finish. Put the end date in the plan.
Segment 2 · Strategy A 0:21

The upside: Oracle starts empty

No old document shape to keep. The first new write lands in a model you chose.

Canonical form→ Projections→ Projected shapes

Model the domain. Project the access. From the first write.

Now the good news. For optimization, this is the best of the three doors.

Oracle starts empty. There's no source document shape to preserve for new data, because the old documents stay where they are. Every new order lands in a model you chose.

So start from canonical form: entities, properties, relationships. Then pick projections: rows on tables, embedded documents, graph edges. Then project the access: a duality view where the app wants its document, rows where the reports want rows, an index where the dashboard wants a Top-N.

Two cautions. The entity data you moved arrives in its old shape, so remodel it in place later; segment 5 shows how. And the app's contract still matters. If the order service returns a document today, a projection returns the same document tomorrow.

Land: age out is the only door where the first write can land in the right model.

Demo 2. Five steps: two in the terminal, three in the console.

Step 1, terminal: copy only the long-lived collections to Oracle. Type:
./lab.sh exec mongo mongodump --archive=/dumps/d2-entities.archive --gzip --db telco --excludeCollection orders --excludeCollection carts --excludeCollection orderEvents --excludeCollection regionTopDevices && ./lab.sh exec mongo mongorestore --archive=/dumps/d2-entities.archive --gzip --nsInclude telco.regions --nsInclude telco.catalog --nsInclude telco.accounts --nsInclude telco.subscribers --nsFrom 'telco.*' --nsTo 'MIG.*' --uri 'mongodb://MIG:MigUser2026@oracle:27017/?authMechanism=PLAIN&authSource=$external&tls=false&retryWrites=false&loadBalanced=true'
Point at the excludeCollection flags: orders, carts, orderEvents and regionTopDevices never leave MongoDB. The restore lands in the pre-created MIG collections. Then Mark done in the console: it checks the counts match the source and that Oracle holds no old orders, carts or events.

Step 2, terminal: age-out mode. Type:
./lab.sh app-mode ageout
The cutoff is the newest legacy order plus one millisecond. Deterministic: same seed, same cutoff, every rehearsal.

Step 3: click 'A new order lands in Oracle' in the console. The order is on Oracle and not on MongoDB, and the subscriber and products it points at came over with the entities. That's the referential seam, handled.

Step 4: click 'One read across the cutoff: MongoDB rows, Oracle rows, merged' in the console. Left pane: MongoDB, before the cutoff. Right pane: Oracle, from the cutoff on. Step 5: click 'Carts expire in MongoDB: nothing to move' in the console. Disclose this out loud: the step plants one cart that was abandoned 125 seconds ago, already past its TTL, so you see a deletion within seconds whatever the generated carts are doing. The rest are real: a 120-second TTL, about 21 carts a minute expiring all session. Oracle has zero carts.

If someone asks about orderEvents: the TTL is on createdAt, a Date. The ts field is a BSON Timestamp, and a TTL index on it would delete nothing. And createdAt is relative to when the data was loaded, so it won't line up with ts. That's on purpose.

If someone asks about the dashboard: in age-out mode its Top-N on Oracle covers only orders after the cutoff, so a region with none shows 'no Top-N'.

And if you do move short-lived data in another strategy, Oracle runs the restored TTL indexes too. Carts keep expiring on Oracle.

Segment 3 · Strategy B 0:27 · 13 min

Dump and restore in a window

Stop writes, move everything, prove it, then flip.

Figure: maintenance window timeline and validation gate
Strategy B is the simplest to explain and the hardest to undo. Open the window, stop writes, mongodump, mongorestore into Oracle, validate, swap the connection string, restart. Once writes land on Oracle, the door is locked behind you.

Equal document counts prove nothing. The validation gate is a type differential per field and a replay of the app's own predicates on both sides. Demo 3 does exactly that, live, and the differential catches a field that reads back identical but fails a type check.
Segment 4 · Strategy C 0:40 · 14 min

Blue/green with a way back

Sync live, flip with no downtime, keep the fallback path open.

Figure: forward sync, cutover, reverse sync for fallback
Strategy C keeps both systems live. A replicator reads the MongoDB change stream and applies every change to Oracle. When lag is near zero, you flip the app. Then you reverse the replicator so changes on Oracle flow back to MongoDB, and the old system stays a real fallback.

In production that replicator is Oracle GoldenGate. On this laptop it's a small stand-in we built, and the console labels it that way. Demo 4 proves no lost and no duplicated writes across the flip.
