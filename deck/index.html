Three doors and one room

Pick by what you can afford to lose, and how long you can be down.

Optimization is not a fourth door. It is the room behind all three.

Start with the axes. Left to right is downtime: near zero on the left, a planned window on the right. Bottom to top is reversibility: a one-way door at the bottom, a door you can walk back through at the top.

Click. Door A, age out. From day N every new write goes to Oracle, and only the long-lived data moves. Near-zero downtime. Slow, because the old system hangs around as a read-only archive until the retention clock runs out. It's a door you close slowly.

Click. Door B, dump and restore. Stop writes, mongodump, mongorestore, validate, flip the connection string. Planned downtime, and fast. Once writes land on Oracle, the door locks behind you. You can delay the lock, and segment 3 shows how. You can't remove it.

Click. Door C, blue/green. Both systems live, a replicator keeping Oracle in step, a flip with no downtime, and a reverse path so you can walk back. The most reversible door. Also the most moving parts.

Click. Now the room. Optimization is not a fourth strategy. It's what you do once you're through the door, and each door gives you a different amount of time and freedom to furnish it. Age out hands you a greenfield. Dump and restore is lift first, remodel in place later. Blue/green lets you remodel during the move, as long as the old document shape is still a projection you can produce for the fallback.

Land: the question isn't how to move the data. It's what you can afford to lose, and for how long you can be down.

Segment 1 · Discovery 0:05 · 10 min

Inventory the workload, not just the data

Ask how long each piece of data stays useful. Some of it never needs to move.

Start with what discovery usually gets wrong. Teams inventory the data: collections, sizes, the index list. Necessary. It's not what picks the door.

What picks the door is how long each piece of data stays useful. The axis is log scale, a minute to ten years. Subscribers, accounts, the catalog, regions: entity data. It lives as long as the customer, and new records point at it. It moves whatever door you pick.

Orders are event data. They age out under a retention policy. With age out they stay behind as a read-only archive. With the other two doors they move.

Now the clocks. orderEvents carry a TTL index, time to live, on createdAt: seven days and the database deletes them. Carts: 120 seconds. In this lab the carts are spread over about four hours after load, so they're expiring while we talk, about 21 a minute. Sessions, rate limiters, caches, carts: transient data never needs migrating. It needs to expire on the side it was born on.

One trap, planted on purpose. orderEvents also carry a field called ts, and it's a BSON Timestamp, not a Date. A TTL index only expires Date values. Put the TTL on the Timestamp and it deletes nothing, with no error. Ours sits on createdAt for exactly that reason.

The rest of the inventory: growth and write rates, every index, feature use (change streams, Atlas Search and $vectorSearch, Atlas triggers, $graphLookup, geo operators, transactions, server-side JavaScript), and your driver and Database Tools versions. Each one changes the plan.

Land: the cheapest bytes to migrate are the ones you let expire.

Segment 1 · Discovery 0:08

Find the landmines before they find you

Five BSON types that survive the move and still change what a query sees.

This is the slide that bites in production. Slow down.

Some BSON types have no Oracle JSON scalar. A regex and a BSON Timestamp land as tagged objects, $regularExpression and $timestamp. Read the document back and it looks right. Now ask for {$type: 'regex'} and the Oracle API rejects the filter: '$type value not supported'. Same for timestamp. A query that found every regex field on MongoDB is an error on Oracle.

Int64. We planted one order whose version is 2^53 plus 1. mongorestore carries it across exactly. Then $inc it by 1 through the Oracle API and it stores 2^53. Exactness gone, no error.

Decimal128. The value survives. The scale doesn't: 19.00 reads back as 19, and 1.10 as 1.1. Equal as numbers, different as text. If a report prints the stored value, format it in the app.

Arrays. On MongoDB, {lines: {$type: 'object'}} matches an order whose lines array holds objects: MongoDB looks inside the array. On Oracle it doesn't. Same data: 2,000 matches on MongoDB, zero on Oracle.

None of this blocks a migration. All of it fails quietly if nobody looks. Demo 1 runs a type census on the source, so you know which fields carry these types before you move a byte. Demo 3 runs the differential after the restore.

Land: reads the same, queries differently. Find them first.

Which door? Start with these factors

Now the factors that pick the door. Read each row as: if this is true, it pushes you toward that door.

Age out: move only what lasts

Day N: new writes go to Oracle. Old orders stay put, read only.

Strategy A, age out. Five steps, and this picture is the first four.

Stand up Oracle. From day N, every new write goes to Oracle. Then move only the long-lived entity data that new records point at. In our lab that's regions, the catalog, accounts and subscribers. Orders stay in MongoDB.

The box on the left is step three: a data access layer in the app tier that routes each read by the cutoff. placedAt on or after the cutoff reads Oracle. Older reads MongoDB. A read that spans both fans out and merges.

Where age out leaks

Every seam is new app code.

Cross-cutoff reads

Fan out to both, merge in the app.

New order, old customer

Move the customer first.

IDs

Keep ObjectId on both sides.

Read-only means read-only

Any write to the old side drifts.

Now the seams. Every seam is new app code, and new code has new bugs.

The cutoff. Where is the line, and is it clean? In the lab it's deterministic: the newest legacy order plus one millisecond. Any query that spans the line fans out to both systems and merges in the app tier. Reports that cross the cutoff are the usual victims: sorting, paging, totals. Demo 2 proves our merged read is correct. Your reports have to prove it too.

Referential seams. A new order references an old customer. That only works if the customer moved first, and that's why the entity versus event split decides the move order.

IDs. Keep ObjectId on both sides, so an _id means the same thing whichever system holds the document. Our router looks up an old order by _id, misses on Oracle, and finds it in the archive.

Read-only means read-only. If anything still writes to the old side, the archive drifts and the merged read serves stale facts. In the lab, a PATCH on an old order returns 400.

And the derived data. Our dashboard's Top-N on Oracle covers only orders after the cutoff, so a region with no new orders yet shows 'no Top-N'. Decide up front whether derived views rebuild from new data only, or get seeded.

Land: age out is cheap on data movement and expensive on seams. Count the seams before you pick it.
Segment 2 · Strategy A 0:20

The cost: a second database for years

The polyglot tax, applied to ourselves.

Way out: when the rest goes cold, move it in one small dump and restore.

The risks. The big one is the one I spend my career warning about in other people's architectures.

Two databases for the life of the window. Two patch cycles, two auth models, two attack surfaces, two sets of backups, two on-call runbooks. That's the polyglot persistence tax, applied to ourselves. Say it plainly to the customer.

Second: 'temporary' archives become permanent. Nobody schedules the decommission, and the retention window keeps getting extended.

Third: the long tail. Seven-year retention means seven years of MongoDB. The way out: once the residue is cold and read-only, move it in one final bulk dump and restore. A small Strategy B at the end, with a window nobody notices, because nothing writes there anyway.

And decide what 'deprecate' means before you start. Frozen and read-only in place, or exported to object storage and queried in place. Pick one in the plan, not in year three.

Land: age out is the gentlest door to walk through and the easiest one to never finish. Put the end date in the plan.
Segment 2 · Strategy A 0:21

The upside: Oracle starts empty

No old document shape to keep. The first new write lands in a model you chose.

Model the domain. Project the access. From the first write.

Now the good news. For optimization, this is the best of the three doors.

Oracle starts empty. There's no source document shape to preserve for new data, because the old documents stay where they are. Every new order lands in a model you chose.

So start from canonical form: entities, properties, relationships. Then pick projections: rows on tables, embedded documents, graph edges. Then project the access, the right-hand column: a rowset for the reports, the order document the app already expects, and a graph result for hierarchy walks like the household and family-plan tree. Point at the dashed line: a duality view hands the app its document straight from the rows, so one fact lives once. The read assembles that document at query time, a join the optimizer plans; the trade is zero write amplification.

Two cautions. The entity data you moved arrives in its old shape, so remodel it in place later; segment 5 shows how. And the app's contract still matters. If the order service returns a document today, a projection returns the same document tomorrow.

Land: age out is the only door where the first write can land in the right model.

Dump and restore: size the window

Stop writes, move everything, prove it, flip. Size it from a rehearsal.

Window = data ÷ measured speed + indexes + checks + a way back.

This is the door most migrations walk through. Same driver, standard tools, one connection string. The work is sizing the window and proving the result. Boring, on purpose.

Strategy B. Dump and restore. The simplest door to explain, and the hardest one to undo.

Here's the whole door on one line. Open the window and stop writes: app down, or app read-only. Click. mongodump with --archive and --gzip: one compressed stream. Click. mongorestore into Oracle, collections in parallel with --numParallelCollections. Click. Indexes. mongorestore rebuilds them from the dump metadata, and you verify they're all there. On Autonomous, a sole-stage $sql running CREATE INDEX is the bridge. Click. Validate. That gets its own slide, because it's where teams cut corners. Click. The rollback buffer: time you hold in reserve to go back if validation says no.

The dashed line is go / no-go. Everything left of it is work. Everything right of it is insurance.

Prepare the target first

Set up the target so nothing fails quietly.

Pre-create schemas

Implicit creation can hit ORA-00600.

Into existing collections.

No database in the URI

Before the window opens, set up the target. Four things, done once, and the restore is boring. Skip them and every card on this slide is a failure that doesn't announce itself.

Pre-create the schemas. The usual advice is to restore as an administrative user and let mongorestore create the schemas for you. Don't. When supplemental logging is on, and it will be if GoldenGate is anywhere in your plan, implicit schema creation can fail with ORA-00600. That's a field hit, August 2026, not a theory. Create the schema, ORDS-enable it, create the collections, then restore.

Which means you restore as the app user. In this lab that's MIG, no admin. mongorestore logs 'restoring to existing collection MIG.orders without dropping'. Nothing gets created, and the indexes are rebuilt from the dump metadata.

Now the trap I want you to remember. Keep the database name out of the URI path. Put /MIG in the path and mongorestore treats it like --db MIG, restores zero documents, and exits 0. Success, with nothing restored. A script that checks the exit code reports green. So assert the restored count is greater than zero, every time. Our restore step does.

Left behind. The dump carries data and index definitions. It doesn't carry users and roles, Atlas Search indexes, triggers, or the change stream consumers hanging off the old cluster. Each one is a line in the runbook, and each line needs an owner.

Land: the restore that fails loudly is the easy one. Hunt the ones that succeed with nothing.
Segment 3 · Strategy B 0:31

Equal counts prove nothing

Check the types and the app's own queries, on both sides.

Verify queries, not documents.

Equal document counts prove nothing. They prove you moved the same number of things. Not the same things, and not things that answer the same questions.

Three checks, in order. One: counts, taken at the dump snapshot. Why the snapshot? Because carts and orderEvents keep expiring, on both sides. The TTL indexes come across in the dump and Oracle runs them too. Compare live counts five minutes apart and they won't match, and nothing is wrong. So compare the dump against what mongorestore says it restored, all eight collections. Necessary. Not enough.

Two: the $type differential. For every field, on both sides: which BSON types are there, and does a $type query give the same answer. Bottom of the slide, from this lab. catalog.skuPattern is a regex. Read the document back from Oracle and it looks identical. Ask for {skuPattern: {$type: 'regex'}} and MongoDB returns 300 documents. Oracle rejects the filter. Same data, different answer. The differential checks values too: the planted Int64 at 2^53 plus 1 comes across exact, and Decimal128 keeps its value with the trailing zeros gone. And on arrays, $type on Oracle doesn't look inside.

Three: replay the app's own predicates against both sides and compare the results. Not a sample of documents. The app's queries. Null versus missing, $first and $last ordering: that's where semantic drift hides, and it only shows up when you ask the questions the app asks.

Then, and only then, flip the connection string.

Land: verify queries, not documents.
Segment 3 · Strategy B 0:33

A one-way door you can delay

Writes on Oracle lock the door. A read-only soak delays it.

Decide before the window: how much would you replay to go back?

Go / no-go. Here's what makes dump and restore a one-way door.

Left box: the window. MongoDB is frozen. Nothing has written to Oracle except the restore. If validation says no, walking back is free: point the app at MongoDB again. Nothing lost.

Right box: writes open on Oracle. From the first committed order, there's data that exists only on Oracle. Now going back means you lose those writes, or you export them by hand and replay them into MongoDB. That's the lock.

You can't remove the lock. You can move it. Middle box: a read-only soak. Flip the app to Oracle with writes still closed. Real reads, the real traffic shape, real plans, while MongoDB stays frozen exactly where you left it. Find the slow query or the type surprise now, and the walk back is still free.

The soak isn't free. It's more read-only time, so the business has to sign off on it. Size it like any other bar in the window.

And decide in advance, in writing: if we have to go back after writes open, how much post-cutover data would we replay, and how? An hour of orders? A day? If the answer is none, then the soak is your last free exit. Treat it that way.

Land: the door still locks. You choose when.

Where blue/green bites

More moving parts.

Oplog window

Must cover the load and the catch-up.

Lag at cutover

Every second of lag is frozen writes.

Split brain

One app still writing to blue.

Index changes on one side only.

Blue/green has the most moving parts of the three doors. Here's where they slip.

The oplog window. The MongoDB oplog keeps a fixed amount of history. It has to cover the whole initial load plus the time to catch up. Size it before you start. If the stream falls off the end of the oplog it can't resume, and you reload.

Lag at cutover. The lag at the moment you drain is how long the write freeze lasts. Cut over when lag is already near zero.

Split brain. One app instance, one batch job, one forgotten cron, still pointed at blue after the flip. Inventory every writer, not just the main app.

Schema drift. For weeks, both systems are live. Somebody adds an index on blue, or a field changes type. Freeze schema changes during the sync window, or apply them to both sides in the same change ticket.

And the bill. Two full stacks for weeks: cost and attack surface. Same tax as age out, shorter window.

One more, specific to Oracle as green. Replication means supplemental logging is on, and that's exactly when implicit schema creation can hit ORA-00600. Pre-create the schemas. Same rule as Strategy B.

None of these is exotic. Every one has bitten somebody who thought the replicator was the whole job. It isn't. The replicator moves the data. People own the parts around it.

Land: name the owner of each card before the sync starts. Not after the flip.
Segment 4 · Strategy C 0:47

Fallback constrains the model

While you might flip back, green must still produce blue's document.

Remodel during the move, as long as blue's shape is a projection.

Here's the constraint that decides whether you can optimize during a blue/green migration.

As long as you might flip back, green has to produce blue's document shape. Exactly. The app's API contract reads it, and the path back to blue writes it. If green stores a better model and can't produce the old shape, your fallback is gone.

So no remodeling until blue is gone? No. This is where duality views earn their keep. Left: normalize the base tables on green. Orders, order lines, subscribers, devices. Middle: a duality view that projects the exact order document blue holds. Right: the app reads the document it always read, and the way back to blue reads the projection, not the storage.

That's UMT in one picture. The canonical form is modeled once. The tables are its projection on green, and the order document is a projected shape. You carry the old shape for as long as the fallback window stays open, and you stop carrying it when the window closes.

Be straight about the trade. The document is assembled at read time. That's a join the optimizer plans, and what you get for it is zero write amplification: change a subscriber's address once, not in every order that copied it.

And the caveat. In 26ai, GoldenGate can replicate duality views as JSON, including to non-Oracle targets. For a MongoDB target, verify it before you claim it. We haven't.

Land: fallback constrains the model. Duality is how you remodel anyway. That's segment 5.

The technical aside, if the room wants it. How does the reverse path avoid echoing forward writes back to MongoDB forever? Capture is a compound trigger on each JSON collection table, writing to a changelog the replicator polls by sequence number. ORDS overwrites CLIENT_INFO on every operation with the MongoDB logical session id of the request. So the forward replicator sends all its writes in one registered session, and the triggers skip that session. A CLIENT_INFO the replicator set itself would never survive ORDS. Proven in the lab: zero forward-applied rows captured, and 200 of 200 app writes captured.

Resilience, if asked: kill the replicator mid-burst with SIGKILL and restart it. It resumes from the saved token, with no lost and no duplicated documents. Tested.
